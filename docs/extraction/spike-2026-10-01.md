# Spike findings — 2026-10-01

## Standard TTS endpoint (`POST /v1/text-to-speech/{voice}/with-timestamps`), voice Rawi, short Arabic text

| | `eleven_multilingual_v2` | `eleven_v3` |
|---|---|---|
| Per-character timings (`alignment.characters` + start/end seconds) | yes | yes |
| `previous_text` / `next_text` (context for smooth joins) | accepted | **rejected** (400 `unsupported_model`) |
| Max characters per request | accepted 6,600 (one ~9 min result) | **5,000** (400 `text_too_long`: "Please use Studio for long form TTS") |
| Response keys | `audio_base64, alignment, normalized_alignment, quality_check` | same |

Decisions that follow:
- `ktab.native-tts.model-id` default = `eleven_multilingual_v2` (context + longer requests; best for joining chunks).
- If the model id starts with `eleven_v3`, the provider sends **no** context and caps a chunk at 4,500 characters.
- Default `max-chars-per-request` stays 2,500 (well under both limits; short requests recover from a failed chunk cheaply).
- Timings use `alignment` (the characters as sent), not `normalized_alignment`.
